# OIDC Launch

An LTI 1.3 launch happens in three requests. Your server handles each one and returns an HTML page;
this package supplies the JavaScript for the first and last pages.

1. **OIDC init.** The platform calls your init URL. The server generates a `state`, tries to set a state
   cookie, and returns a page that calls **`initOIDCLaunch`**. That saves the `state` and sends the browser
   back to the platform's authorization endpoint.
2. **Redirect.** The platform posts the ID token to your redirect URL. The server validates it (server side
   only) and redirects to the launch.
3. **Launch.** The server validates the request and checks for the state cookie, then returns your app's
   page, which calls **`ltiLaunch`** to confirm the `state` saved in step 1.

The client-side storage of `state` follows the
[LTI OIDC Login with LTI Client Side postMessages](https://www.imsglobal.org/spec/lti-cs-oidc/v0p1)
spec, so launches work even when the browser blocks third-party cookies inside the LMS iframe.

:::tip
[`@atomicjolt/lti-server`](/lti-server/) builds the settings objects used below, and
[`@atomicjolt/lti-components`](/lti-components/) wraps `ltiLaunch` in a React component.
:::

## Step 1: `initOIDCLaunch`

```ts
function initOIDCLaunch(settings: InitSettings): void;
```

Call it from the page returned by your OIDC init endpoint, usually with settings the server rendered into
the page:

```ts
import { initOIDCLaunch } from "@atomicjolt/lti-client";
import type { InitSettings } from "@atomicjolt/lti-client";

const settings: InitSettings = window.INIT_SETTINGS; // rendered by the server

initOIDCLaunch(settings);
```

The page must contain an element with `id="main-content"`; messages for the user are rendered into it.

When the window's `load` event fires, it:

1. Redirects to `responseUrl` straight away if the state cookie (`openIdCookiePrefix + state`) is present.
2. Otherwise writes the `state` to platform storage (`lti.put_data`, under the key `aj_lti<state>`) and then redirects.
3. If that fails and the page is in an iframe, shows an "Open in a new window" button (which opens
   `relaunchInitUrl`) and, if the browser has the Storage Access API, a link to request cookie access.
4. If that fails and the page isn't in an iframe, shows a "Cookies Required" message.

If nothing has happened within 5 seconds, it adds a generic "There was an error launching the LTI tool"
message. Messages use the browser's language (English, Spanish or French; `?lng=` in the query string
overrides it).

### `InitSettings`

| Field | Type | Description |
| --- | --- | --- |
| `state` | `string` | The OIDC `state` generated by the server for this launch. |
| `responseUrl` | `string` | The platform's authorization URL with all OIDC parameters; the browser is sent here to continue. |
| `ltiStorageParams` | `LTIStorageParams` | Where to reach platform storage (see below). |
| `relaunchInitUrl` | `string` | URL that restarts the launch; opened by the "Open in a new window" button. |
| `openIdCookiePrefix` | `string` | Prefix of the state cookie name. The cookie checked is `${openIdCookiePrefix}${state}`. |
| `privacyPolicyMessage` | `string?` | Replaces "We use cookies for login and security." in the cookie messages. |
| `privacyPolicyUrl` | `string?` | Intended for the "privacy policy" link in the cookie messages. Currently not applied: the link's `href` is left as the literal `{{url}}`. |

### `LTIStorageParams`

| Field | Type | Description |
| --- | --- | --- |
| `platformOIDCUrl` | `string` | The platform's OIDC authorization URL. Its origin is used as the postMessage target origin. |
| `target` | `string?` | Name of the frame that handles platform storage. If omitted, it's looked up from the platform's `lti.capabilities` response, falling back to the parent window. |
| `originSupportBroken` | `boolean?` | Post messages with target origin `"*"` instead of the platform origin. Needed for platforms (such as Canvas) that don't support the spec's origin yet. |

## Step 3: `ltiLaunch`

```ts
function ltiLaunch(settings: LaunchSettings): Promise<boolean>;
```

Call it from your app's launch page before showing the app. It resolves `true` when the launch's
`state` is verified:

- If `stateVerified` is `true` (the server already found a valid state cookie), it resolves `true`
  immediately.
- Otherwise it reads the `state` back from platform storage using `ltiStorageParams` and resolves `true`
  if it matches. It resolves `false` if they don't match, if there are no `ltiStorageParams`, or if the
  platform doesn't answer within 2 seconds. It never rejects.

```ts
import { ltiLaunch } from "@atomicjolt/lti-client";
import type { LaunchSettings } from "@atomicjolt/lti-client";

const settings: LaunchSettings = window.LAUNCH_SETTINGS; // rendered by the server
// e.g. { stateVerified: false, state: "…", ltiStorageParams: { platformOIDCUrl: "https://canvas.instructure.com/api/lti/authorize_redirect", originSupportBroken: true } }

const verified = await ltiLaunch(settings);

if (verified) {
  renderApp();
} else {
  showError("This launch could not be verified. Please relaunch the tool.");
}
```

### `LaunchSettings`

| Field | Type | Description |
| --- | --- | --- |
| `stateVerified` | `boolean` | `true` if the server already verified the state (via the cookie). |
| `state` | `string` | The launch's `state`. |
| `ltiStorageParams` | `LTIStorageParams?` | Needed to verify the state through platform storage. |
| `jwt` | `string?` | Not used by `ltiLaunch`; available for passing your app's token to the page. |
| `deepLinking` | `DeepLinkingClaim?` | Not used by `ltiLaunch`; available for passing the deep linking claim to the page. |
