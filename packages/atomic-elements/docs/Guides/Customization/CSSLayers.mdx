# CSS Layers

Atomic Elements puts all of its styles, including the theme's CSS variables, in a
[CSS `@layer`](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer) named `elements`. This
gives you explicit control over how library styles interact with your own CSS, and means your own
unlayered CSS always wins.

## Why use CSS layers?

Without layers, overriding library styles requires matching or beating their specificity — which often means
adding extra selectors, using `!important`, or relying on source order. CSS layers solve this cleanly:
styles in a lower-priority layer are always overridden by styles outside any layer, regardless of specificity.

```css
/* What the library ships (simplified): a fairly specific selector, inside the layer */
@layer elements {
  .sc-a1b2c3.aje-btn--primary {
    --btn-bg-clr: var(--accent-clr-fill);
  }
}

/* Your CSS, for <Button className="my-button">: a single class, outside any layer.
   It wins, despite lower specificity. */
.my-button {
  --btn-bg-clr: darkslateblue;
}
```

## Default behavior

Layering is on by default. `ElementsProvider` wraps every style rule it injects in
`@layer elements`, with no configuration needed:

```tsx
import { ElementsProvider } from "@atomicjolt/atomic-elements";

const App = () => (
  <ElementsProvider>
    <YourApp />
  </ElementsProvider>
);
```

## Customizing the layer name

Use the `layerName` prop to change the layer name. This is useful when you need to coordinate
layer ordering with other style sources:

```tsx
<ElementsProvider layerName="ui">
  <YourApp />
</ElementsProvider>
```

## Controlling layer order

Declare your layer stack at the top of your global CSS to lock in the cascade order:

```css
/* Establish layer order — last layer wins */
@layer reset, elements, overrides;
```

With this in place, any styles you write outside a layer (or inside `@layer overrides`) will
always take precedence over `@layer elements`, making it straightforward to customize
component styles without fighting specificity.

```css
@layer reset, elements, overrides;

@layer overrides {
  /* These always win over @layer elements, no !important needed */
  .aje-btn--primary {
    --btn-bg-clr: indigo;
    --btn-hover-bg-clr: darkslateblue;
  }
}
```

## Overriding with plain CSS

Styles written outside any `@layer` have higher priority than any layered style by default.
This means you can override component styles with ordinary CSS rules, even ones with lower specificity:

```css
/* No @layer declaration needed — unlayered styles always win */
.my-button {
  --btn-bg-clr: green;
}
```

## Browser support

`@layer` is supported in all modern browsers (Chrome 99+, Firefox 97+, Safari 15.4+).
In older browsers the whole `@layer` block is skipped as an unknown at-rule, so components would
render unstyled.
If you need to support older browsers, turn layering off by passing `null` or an empty string as
`layerName`:

```tsx
<ElementsProvider layerName={null}>
  <YourApp />
</ElementsProvider>
```

With layering off, component styles compete on specificity again, so overrides need selectors
more specific than the library's (see [Variants](./Variants.mdx#changing-a-built-in-variant)).

## Upgrading from before 3.7.0

Before `3.7.0`, component styles were unlayered. Turning layers on can change the outcome of app
CSS that used to lose to component styles, such as a broad `a { color: inherit; }` reset now
overriding a link-styled `Button`. See [Migrating](../../Migrating.mdx#styling-with-css-layers).
